# Inventory editor — product specification

## Confirmed scope

- The inventory editor is a comprehensive local save editor, separate from collection registration. The inventory has no fixed UI slot or page capacity.
- Use the original game inventory category order and mappings. For category navigation, prefer distinct full-color, game-derived representative artwork whose motif and silhouette resemble the original game's category icon (existing collection category art or an actual representative item's native UiIcon). A representative is a visual affordance and need not belong to the category it depicts; native classification is unaffected. Use the shared colorway artwork pipeline for dyeable representatives without claiming unverified exact fidelity. Prefer these images rather than uniform monochrome inventory tab icons or identical circular backgrounds. If no verified representative is available, retain a readable text label. Keep unknown records visible without inventing a category or dropping them.
- Display a dense, responsive, image-first grid with item name and owned quantity. Use compact controls, native item artwork, search and automatic incremental scrolling; no repeated technical labels or unused slot placeholders. Search shows matching record counts on native category tabs and reveals the first matching category if the current one has no match, while keeping manual category selection available. The same search operates in owned and add modes; an edit or snapshot refresh never itself changes the selected category for search.
- Allow users to edit ordinary inventory quantities and the native unique data of flowers, customizable furniture and customizable clothing. Unique-data editing is a confirmed product requirement, even while individual operations are not yet supported.
- For flowers, display the original color swatch and pattern/effect sprite above the item image, with localized color and pattern names sourced from the game. Render the actual variant when its native dynamic-color composition is verified; do not represent an unmodified species sprite or approximation as an exact variant.
- Preserve distinct native records with different unique data; do not merge them merely because they have the same Item ID. Show the appropriate variant appearance when verified source data permits. Use the shared on-demand browser image generator for appearances without a completed original, including flowers, customizable furniture and palette-dependent items; do not ship pre-generated combinations. Reuse generated output only for the same source version, rendering revision and appearance attributes. Other unique-data types are in scope for imagery if native rendering is appearance-dependent; a unique payload alone does not prove a visual difference. Expose individual customization controls on demand rather than enlarging every inventory tile.

## Safety and implementation constraints

- Rust is the sole authority for native schema interpretation, valid options, version/structure gates, CAS, atomic mutation, history, undo/redo, reconstruction and independent reparse. Svelte/TS only render and relay typed intents.
- Use source-verified game definitions for each supported unique-data discriminator, field, type and valid option. Do not infer flower genetics, color/pattern encodings, customization choices or IDs from display names or approximate images.
- Keep Document ID, Item ID, Unique ID, quantity, unrelated data and unknown payload fields unchanged unless an explicitly supported operation requires changing one of them. Do not invent identities or native payloads.
- Distinguish the inventory item's individual customization from collection history, placed furniture, equipped clothing, and entitlement or reward state. Do not silently mutate those other systems.
- Each unique-data edit must participate in the existing inventory history, recovery draft, Undo/Redo and export/reparse path; unsupported variants/fields remain read-only until verified.

## Current implementation boundary (not a reduction of scope)

The v3.0.1 native inventory index recognizes Document ID, Item ID, Unique ID, quantity and optional InventoryUniqueData. The Rust quantity writer accepts supported ordinary stacks with a nil unique payload and source-verified existing flower, flower-crafted clothing, customized furniture, custom palette and chef variants (positive quantity only). The native schema walk retains exact source spans and top-level field spans for all 12 unique union variants. The flower variant edit slice supports existing seeds, plucked flowers and grown-troweled plants with nonconflicting identities. Base color, pattern/effect and pattern color are editable within native source-bounded choices; growth state is preserved. Unsupported unique fields remain read-only. The current Rust schema and inherited [v3.0.1 native schema](https://github.com/Yumekiraboshi/HKIA-Editor-Dev/blob/main/scripts/research/native-v301-dbroot-schema.json) agree on these native union variants:

| Tag | Type | Serialized fields in order |
| --- | --- | --- |
| 7 | FlowerUniqueDataV2 | FlowerGrowState (byte), FlowerColorIndex (int), FlowerPatternIndex (int), FlowerColorIndex (int) |
| 8 | FurnitureUniqueDataV2 | FurnitureMaterialIndex (int) × 3 |
| 6 | PaletteUniqueData | Color (four float32 components) × 3 |

Tags 1 and 2 are deprecated furniture/flower types using Hash128, not interchangeable with V2. PaletteUniqueData is a native color payload and appears in the shared union used by outfit models; this does not prove that every customizable clothing Item ID uses that payload. Field positions and storage types are known, but the valid option values, per-item applicability, semantic roles of the two flower colors, and native identity/reference behavior are not established by the schema alone. Do not expose arbitrary numeric index or color edits as valid game choices. Preserve opaque and deprecated payloads pending evidence.

Implementation reference: `core/src/schema.rs`, `core/src/native.rs`, `core/src/collection.rs`. Reuse the current native index and session, not the historical JS research reader.

### Variant-aware search

The existing inventory search and native category match counts reuse each displayed localized flower color/pattern title, keyed by the Rust document identity. Whitespace-separated terms can combine the item name and appearance labels; unknown labels are not invented. This is presentation-only and applies to existing flower and flower-crafted clothing payloads, not new item creation.

### Native inventory UI assets (v3.0.1)

`public/inventory-ui/index.json` records original source references and exact decoded-pixel verification of all thirteen category sprites and sixteen flower pattern/effect sprites. The original category sprites are retained as source assets, not the default navigation artwork. The flower color and pattern definitions and all 16 locale label maps derive from native assets. Game acceptance of the edited save still requires verification.

### Native unique payload and edit boundary (v3.0.1)

Switch original NSO SHA-256 `64bd5fb69239f57eb0578a1897a45a3c6f5e187480903f83df503b46bf827bfb`. The original IL2CPP metadata identifies runtime `Inventory.SetItems` at 0x399A710. The existing-item path at 0x399AA08–0x399AAA8 selects by Item ID, compares UID at 0x399AA78–0x399AA84, copies the incoming UniqueData at 0x399AA88–0x399AA9C, and updates quantity at 0x399AAA0–0x399AAA4. This establishes native in-memory replacement by identity, not an entitlement grant or proof of game acceptance of an externally edited save. `FlowerUniqueDataV2` uses GrowStateSerialized, ColorDefIndex, PatternDefIndex, PatternColorIndex. `FlowerGrowState.Plucked=6`, null pattern/color index=0. Rust uses the source-bounded choices described below, rejects ambiguous UID, known direct and legacy UID references, opaque same-species peers and original/effective target variant collisions. No new UID, quantity, ownership or entitlement is written. The conservative boundary does not establish complete reference closure for all game systems; runtime validation remains pending.

The schema also defines tag 0 schematic GUID, tag 1 legacy furniture, tag 2 legacy flower, tag 3 cafe flavor/color lists, tag 4 boba characteristics, tag 5 legacy wand, tag 9 wand with nested source unique data, tag 10 home layout and tag 11 home kit. All 12 source payloads are retained; typed field editors for the remaining types require their native validity and identity rules. Home-layout editing remains subject to the separate product scope.

#### Flower variant choices

Exclude those two until event eligibility is established. The native restriction check is at Switch NSO RVA 0x4a7f7e0; `FlowerUniqueData.FlowerColorsPassRestrictions` (0x332bdb0) checks both primary and non-null secondary colors.
- The 25 species and their default/crosstype patterns come from `core/data/inventory-flower-definitions-v3.0.1.json`. Exclude patterns 6 and 15 requiring DLC. `FlowerBreederHelpers.AddCrosstypePatterns` (0x422b160) reads the species CrosstypePatterns list and assigns secondary color only for a non-effect pattern. `FlowerSettings.GetPatternColor` (0x4a76830) selects White (16), or WarmPink (17) if the primary is White. A non-effect secondary color must differ from the primary. These bounds do not prove every candidate is obtainable by breeding.
- Native equality (0x332ba70) compares growth state and three normalized definition hashes. Preserve the existing growth state (supported states 0, 6, 7); update only changed source field spans. Restrict unverified references and collisions. Pattern and related secondary-color changes form a single CAS/undo operation. The editor exposes 28 unrestricted colors, species-specific subsets of 14 non-DLC patterns, and no-pattern. All actual game-load acceptance and complete reference closure remain unverified. The edit hint is not a mutation authorization; options and CAS check the full target on demand.

#### Positive quantities of existing flower and flower-crafted clothing variants (v3.0.1)

The 25 source species in FLOWER_SPECIES and the 27 verified flower-crafted clothing outputs described below have original definition flags Stackable + RequiresUniqueData without a custom cap (rule value 3). Native MaxCount returns Int32.MaxValue for this case; existing Inventory.SetItems writes quantity by Item ID and UID as described above. Rust permits quantities 1 through Int32.MaxValue only for full tag-7 source species in states Seed (0), Plucked (6), GrownTroweled (7), or the verified flower-crafted clothing outputs in state 6 with verified unrestricted color/pattern values, positive unique ID, no duplicate UID, no ambiguous/equal original peer, and no known direct, legacy or copied-payload reference or unresolved payload reference. The original identity eligibility index is built once; variant editing reserves both original and effective identities. Quantity and appearance can be edited independently through the same scoped history and export path, preserving the payload bytes unless explicitly edited. No new unique ID, record, event color, entitlement, growth-state change or zero-quantity operation is authorized. Synthetic raw/ZIP and Chromium tests cover the operation; actual game acceptance remains unverified.

#### Furniture material choices (v3.0.1)

The original material and item-slot crosswalk is described in [inventory-furniture-source.md](../inventory-furniture-source.md). The existing tag-8 furniture writer exposes only Rust-authorized changes to one material slot at a time, keeping the other slots, item ID, document ID, UID and quantity unchanged. It rejects invalid slot choices, known direct or legacy references, opaque or legacy peers, normalized variant collisions, home-layout definitions, locked pattern materials and the all-null target. It does not create a new item, unlock patterns, modify placement, or grant ownership. The editor uses native-source UI color swatches as selection aids; they are not exact furniture renders. Internal source material labels are temporary until original localized display names are resolved. The same inventory history, local draft and independent export reparse paths apply. Synthetic tests do not establish game acceptance or complete reference closure.

#### Positive quantities of existing customized furniture (v3.0.1)

The original quantity definition rules and furniture slot crosswalk intersect at 621 non-home-layout customizable furniture definitions, all stackable without a custom maximum (326 flag 1; 295 flag 17). The quantity operation accepts complete existing tag-8 records only if the existing furniture source validator accepts the material tuple, its native UID is unambiguous, known direct/legacy/copied references and unresolved payload references are absent, and the source-normalized variant is unique among original peers (including nil ordinary rows). The shared original identity index also rejects opaque peers. Rust issues bounds 1 through Int32.MaxValue and reuses native quantity CAS, batch, history, recovery and export/reparse. Quantity-only edits preserve the exact original unique payload. Material edits reserve original/effective variant identities and can be combined in the same session. No placement, home layout, material unlock, new UID, or zero-quantity operation is authorized. The compact card provides both quantity and material editing. Actual game acceptance remains unverified.

#### Positive quantities of existing custom palettes and chef creations (v3.0.1)

The exact Item IDs in the pinned [palette](../dynamic-palette-art.md) and [chef](../dynamic-chef-art.md) source manifests (one custom palette, nine cafe creations, one Boba tea) all have definition flags 3: Stackable + RequiresUniqueData with no custom cap. A quantity-only operation supports a complete corresponding tag 6, 3 or 4 payload with a single saved row for that Item ID, positive unique UID, no ambiguous UID or known direct/legacy/copied references, and no unresolved reference flags. Palette RGBA words must be finite and normalized; chef colors must be present in the original characteristic-to-swatch crosswalk, including the entire saved cafe color list rather than its display prefix. The original flavors and other fields are retained byte-for-byte; the editor does not infer their valid choices. Multiple rows sharing an Item ID remain read-only until native equality is verified. Existing Rust CAS/batch/history/draft/export paths and compact quantity controls apply. No zero, new UID, flavor/color mutation or game-load acceptance is authorized.

#### Unique flower creation from existing species (v3.0.1)

Inherited original Switch analysis, [factory/hydration receipt](https://github.com/Yumekiraboshi/HKIA-Editor-Dev/blob/main/coordination/state/streams/09_INVENTORY/parts/002.json) (delta SHA-256 6a84f82fea4d34264a8f852ab4c9916f913899c544baa71ed310c4cf92e25101, independent static evidence a4de00865779bc6336aacaa695a17744b6100e7530f9b7d54bb2950a1f78763b), establishes the signed maximum of saved UniqueId values with seed zero. [Concrete transfer receipt](https://github.com/Yumekiraboshi/HKIA-Editor-Dev/blob/main/coordination/state/streams/09_INVENTORY/parts/005.json) (delta SHA-256 776d6d0e334d44a5dde5580a22a75ea4f0faaea04fef09ac0c061fa0a935cb55) independently verified that unmatched UID-zero/non-nil items increment largestUniqueId. The shared allocator uses checked max+1, rejects incomplete/duplicate identities and known reference collisions, and is distinct from DbRoot.NextId.

The first core operation stages a different source-valid tag-7 tuple with the same growth state as a validated existing flower species row. Existing identity and quantity remain unchanged. Multiple staged variants use distinct session-only handles disjoint from ordinary candidate handles; native UIDs and document IDs are assigned only at export, reparse validates both. Original and effective peer tuples plus staged tuples are reserved; no copied/reference ambiguity, crafted clothing grants, restricted color/pattern, zero or speculative UID is allowed. Quantity adjustments, history replay, Undo/Redo and raw/ZIP reparse are covered by synthetic tests. The existing flower dialog offers Add items only for Rust-issued creation choices. An explicit Add stages quantity one; the compact quantity controls adjust the staged row, and Undo removes the staged creation. Multiple variants can be staged. The local net-change view preserves typed creation identities for comparison, but only the native checkpoint can restore them (no inferred fallback source). The native journal refuses further edits that would evict a staged creation or its prerequisites. Real game acceptance remains unverified.

#### Ordinary quantity batch editing

The existing-stack quantity batch uses the same Rust CAS gate as individual quantity editing. Selection is an explicit temporary mode, with compact cards and original category browsing retained. Each accepted transaction edits only existing ordinary stacks and writes one scoped history entry, listing every changed quantity; unsupported unique payloads, creation and deletion are excluded. All requested rows must validate before any write. The first implementation permits up to 40 selected stacks per transaction to preserve the existing bounded native history checkpoint (256 steps, 128 KiB); this is not an inventory capacity or pagination limit. No-op rows are validated and omitted from the transaction. Individual and grouped history remain recoverable from the same native checkpoint and export path.

### Native document membership allocation (v3.0.1)

Original Switch IL2CPP metadata (dump.cs SHA-256 `4b4eb6a543722e1dfaf8aad5593e9e1300723aff55e9e750d489744960feb738`) identifies `MessagePackCollectionProvider.DbRoot` Key(1) as `NextId`, not a document count. Original NSO `Insert<T>` (RVA 0x621EA20, allocation at 0x621EB1C–0x621EB30) and `Upsert<T>` (RVA 0x621F3C0, allocation at 0x621F60C–0x621F620) increment this counter before assigning the new ID for an unallocated entity. New source-authorized document creation must use the shared counter, not the maximum ID within one tag. Rust rejects overflow and collisions against existing document IDs; insertion increments the stored counter and rewrites the root array atomically. Deletion does not rewind the counter. These structural rules are shared with achievement creation; they do not establish permission to create/delete a particular inventory item or prove game acceptance.

#### Emptying and replenishing ordinary material stacks

Original Switch v3.0.1 `Inventory.RemoveItems` at RVA 0x3999A70 (identity comparison and clamp/store at 0x3999DE8–0x3999E28) subtracts from the matching runtime item and clamps to zero rather than deleting its record. `ClientInventoryManager.SaveInventory` selects and converts the inventory to saved models and preserves existing document IDs by Item ID and UID match (0x3987220–0x3987240). The first zero-quantity operation supports only the 37 ordinary ingredient candidates from [inventory-quantity-source.md](../inventory-quantity-source.md), a single full UID-zero nil row, and no known direct reference or incomplete legacy reference data. Zero remains a native saved record, not a physical deletion or a change to collection/placement/quest/entitlement state. Rust issues both bounds, validates each CAS and revalidates export. Users can refill a saved zero row and clear eligible rows individually or in a group after confirmation. Native ID allocation for entirely absent records is a separate operation. Game-load acceptance is not yet verified.

### Absent ordinary ingredients (3.0.1)

The source-bounded ingredient allowlist also supports addition of previously absent rows. Native ServerInventoryAccessTrait.AddItem constructs ItemId, UID zero, quantity and nil unique data for ordinary items; Inventory.AddItems allocates a runtime UID only for a non-null unique payload. SaveInventory projects the native tuple into InventoryItem and retains an existing ID on matching ItemId/UID; new documents are allocated via DbRoot.NextId. The editor stages additions with disjoint session-only handles and never persists these handles. Rust authorizes candidates, refuses ambiguous or already present items and known references, reserves shared document IDs across both history scopes, and verifies the final export by reparse. Add mode reuses the native category and quantity/batch controls. Clearing a not-yet-exported addition cancels it; clearing a previously saved eligible row preserves its native zero-quantity record. No quest, reward, collection, DLC, or entitlement fields are changed. The initial scope is 37 verified ordinary ingredients, not all items; actual game-load compatibility remains unverified.

#### Ordinary furniture and clothing creation

The absent-stack addition flow extends to 1,114 ordinary furniture and 2,435 ordinary clothing definitions. The source-verified 4,046 creation candidates remain independent from existing-stack zero-quantity eligibility (497 ordinary materials, fish, critters, food and bait). Staged additions can be cancelled, but deleting the last persisted furniture/clothing copy requires verified equip/placement reference closure. Absent cosmetic candidates are also rejected when the existing typed copied-payload index contains their Item ID or reports unresolved legacy payload references; Rust applies this check in candidate listing, CAS, batch CAS, recovery and export. Ordinary material/gathered/food/bait creation retains its separate source gate. The same Rust source gate, native allocator, history, local draft, UI and export/reparse are used. For the 295 customizable non-home-layout furniture definitions that also qualify for ordinary creation, an absent UID-zero base stack can be added alongside existing verified nondefault tag-8 variants. Every original peer must qualify for the shared unique quantity identity/reference gate, and its original and effective source-normalized material tuple must differ from the default. Existing ordinary/default/opaque/ambiguous peers still block creation. Staged ordinary rows reserve the normalized default in furniture CAS/options/export; cancelling or undoing the addition releases that reservation. This adds an ordinary native row without creating a new unique ID or changing existing variants. See [inventory-quantity-source.md](../inventory-quantity-source.md).
