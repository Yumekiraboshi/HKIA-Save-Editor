# HKIA Save Editor — 製品仕様

本書は現在作るべき製品の正本であり、実装済み機能の一覧や進捗報告ではない。技術構成・安全性・開発運用は [ENGINEERING_CONTRACT.md](ENGINEERING_CONTRACT.md) に従う。Owner が承認した変更を決定した担当者が、本書または関連する詳細仕様へ反映する。未実装を理由に確定した機能を削らない。

## 1. 製品の目的と範囲

ゆめきらぼしの HKIA Save Editor は Hello Kitty Island Adventure のセーブをブラウザ内で安全かつ直感的に編集するツール。対象はコレクション、アチーブメント、インベントリー包括編集、Layouts（バックアップ・復元および第2段階の2D配置編集）の4領域。アカウント、コミュニティ、クラウドセーブ、セーブを必要としない閲覧サービスは対象外。庭園、アバター、フレンド、クエスト等の独立編集は現時点の確定範囲に含めない。

## 2. 共通画面・操作

- 初期画面はセーブ選択／ドロップを主とする。対応するセーブの読込後に編集画面へ移る。エラー・非対応状態は簡潔で操作可能な形で表示する。
- ゲーム画面のようにビューポート全体を作業領域として使う。画像・SVG アイコンを活用し、説明・技術情報・装飾や常設のヘッダー／フッターによる領域消費を最小化する。利用者に内部 ID やデバッグ情報を常時表示しない。狭い画面やキーボード操作も考慮する。
- セーブ読込後のコレクション・アチーブメント・インベントリー等の一覧画面、共通ヘッダー・操作バーはビューポート幅全体を利用する。デスクトップの左右には最小限の余白（原則24px、狭い画面は縮小）を残し、広い画面では画像や操作部品を過度に拡大せず列数を増やす。編集ダイアログ・削除確認等の集中操作とセーブ未読込画面は適切な最大幅で中央寄せとする。
- 公開リポジトリの利用者向け README は不要。操作説明を読まなくても使える UI を目指す。必要な説明・警告・確認は該当操作の画面内で簡潔に提示する。権利帰属の簡潔な表記はセーブ読込前に置き、編集中の常設表示はしない。
- 共通のファイル選択、原本バックアップ、別ファイルへの書き出し、Undo/Redo、編集履歴、検索、言語選択を一貫した操作にする。編集履歴は各機能ごとに変更内容を確認でき、任意の地点へ戻す／進めることができる。原本・未書き出しの変更を失う操作には適切な保護を設ける。ローカル復旧と履歴は共通基盤で扱う。ページ再読み込みでセーブセッションが復旧した場合、直前に使用していた機能（コレクション・アチーブメント・インベントリー・Layouts）を復元する。機能選択は同一ブラウザタブ内に保持し、セーブの内容や編集履歴には含めない。
- 登録済み／達成済みの解除など日時を消失させる操作は、クリック後の確認を経て変更する。対応できない機能は無効化し、利用可能と誤認させない。
- ゲームの全対応言語を対象とする。ゲームの正式名称・分類を優先し、言語の変更で編集状態を変えない。

## 3. コレクション

- ゲーム内のコレクション分類・順序を基礎にカテゴリー、必要な下位分類、アイテム一覧を提供する。記録が一件もないカテゴリーや未登録アイテムも表示する。
- 各階層で検索できる。アイテム画像、正式名称、登録状態を中心に表示し、一覧はスクロールで遅延読み込みする。色違い等の個別記録も扱う。
- 登録・解除と登録日時の編集を提供する。登録履歴と実所持、実取得、報酬、レシピ、ゲーム進行、DLC 権利は同一視しない。関連データの更新は操作の意味と必要性が原本から確認された場合に限り原子的に扱う。保存形式・ゲーム版・実証済み識別子に基づき編集可能性を判定する。

## 4. アチーブメント

- ゲームのカテゴリー構成・進行順序を尊重し、カテゴリー全体の実績を配下の個別実績として重複表示しない。カテゴリーと個別実績に正しく対応するゲーム由来画像を使用する（原本に存在しない画像は捏造しない）。
- 検索以外の余分な絞り込み UI は設けない。個別一覧は「続きを表示」ボタンではなくスクロールで自動読み込みする。達成状況を簡潔に確認できるようにする。
- 達成・解除、達成日時の編集を提供する。任意の進捗数値入力 UI は設けない。達成状態に応じた内部進捗値は確認済みのゲームルールに従う。
- 個別保存記録が存在しないことと未達成／未確認の意味を区別し、原本により正しい状態表示ができるものを不必要に「不明」としない。確認済みの欠落記録の生成はユーザーによる編集時に限る。
- カテゴリー内のすべての個別実績を達成した場合はカテゴリー全体も達成扱いにする。親子関係を正しく保ち、親の解除・日時同期も検証済みの関係に従う。日時の由来を確認できない場合は捏造しない。最新の子達成日時を使用するルールは、日時が揃い親の日時の意味が確認できる範囲で扱う。
- 取得条件や説明の充実は製品の目的ではない。報酬・ゲームカウンター・オンライン実績・権利の変更を達成フラグの編集と混同しない。

## 5. インベントリー

- 同一のネイティブ保存構造・編集セマンティクスを持つアイテムは、原本の定義と共通のRust判定により構造単位で一括して対象化する。個別Item IDや表示カテゴリーごとの許可追加を開発手順としない。数量操作、個体属性の編集、新規生成の制約は分離し、個別の制限は原本で確認された固有仕様・参照・権利等に限る。全原本定義を横断する検証で対応漏れを検出する。
- 実装順序は、ユニークデータなしの全通常アイテムの包括編集を先に完成させ、その後ユニークデータ付きの全保存構造を完成させる。必須ではないが実際に個体データを持つ家具等は後者に含む。
- 現在の最優先実装は、全アイテム（ユニークデータ付き含む）の既存エントリーの数量変更・数量0化・物理削除を網羅すること。属性編集・新規追加・機能連動より先に進める。原本に根拠のある上限・参照・特殊状態の安全制約は維持する。有限上限の同一Item IDの複数行も、共通の数量上限と全体数量検証で編集し、一律無効化しない。開発全体の目標は、ゲーム内インベントリーの全アイテムについて追加・編集・削除を実装すること。全種類のネイティブユニークデータ（個体属性・バリエーション）も対象とする。未対応領域の実装をUIの細部改善より優先する。安全性・原本根拠・参照整合性の要件を維持し、DLC権利、報酬、ゲーム進行等の別の状態は推測して生成しない。

- 通常のセーブ内所持品全体を対象とする。ゲーム内インベントリーのカテゴリーとその表示順を採用し、カテゴリー別に管理・検索できるようにする。カテゴリーのナビゲーション画像は視認性を優先し、ゲーム内のカテゴリーアイコンとモチーフ・形状が近い、ゲーム由来の色付き代表画像（コレクション用画像または代表アイテム画像）を用いる。代表画像は視覚的な案内であり、アイテムの所属分類を変更しない。ゲーム内の単色カテゴリーアイコンや共通の円形背景を強制しない。コレクションの分類とは区別する。
- 数量0の保存済みスタックは通常一覧・検索ともに初期状態では非表示とする。「数量0を表示」オプションで表示できる。アイテム追加画面では補充可能な数量0のスタックを引き続き利用できる。表示設定はセーブデータに影響しない。
- ユニークデータは完成済みの組合せ選択だけでなく、各パラメーターを個別に編集できるようにする。花は種類・状態・ベースカラー・エフェクト・パターン・パターンカラーを対象とする。ネイティブで排他的な属性や連動が必要な属性はその制約を保ち、変更を明示する。種類変更は Item ID の変更として Rust が参照整合性を検証する。全ユニークデータ構造に同じ個別編集方針を適用する。
- Item ID 単位の正式名称・画像と所持数量を表示する。スタックと個体、個別属性、装備中／配置中／予約中／クエスト関連の参照、取得履歴、アンロック、権利を区別する。
- ユニークデータ付きアイテムの一覧・プレビューは、保存構造ごとに識別しやすく最適化する。花と花由来アイテムのカラー補助表示は、確認済みのパターンカラーがある場合、円形バッジの左上をベースカラー、右下をパターンカラーとする。単色・色を持たないエフェクトは単色とし、パターン／エフェクトの既存円形マークは別に維持する。家具・家具由来の杖は原本アイコンと個体の材質スウォッチ・材質名を併用し、色で柄や材質を完全に表せるとはみなさない。カスタムパレットは実際の3色を順序通り表示する。料理・タピオカティー・杖は原本に基づく個体アイコンを優先し、画像に表れない材料・甘さ・ミルク・粒子等の識別に必要な情報を簡潔に補う。間取り・ホームキットは確認済みの保存名を表示し、設計図・未解決の個体属性を推測表示しない。これらはエディター用の補助表示であり、ゲーム原本画像の生成仕様やセーブ編集可否を変更しない。
- 実装単位は Item ID や表示カテゴリーではなく、ネイティブな保存構造とゲーム原本の定義・制約とする。通常（nil）レコードの追加・削除・数量変更は共通処理で、ユニークデータはネイティブ Tag と payload 構造ごとに共通処理を整備する。全原本定義から規則と参照情報を機械的に生成し、個別アイテムの許可リストを段階的に増やす開発方式を原則廃止する。実証済みの特殊制約は構造・属性・参照の検証に用いる。
- 通常アイテムの個別・一括追加、削除、数量変更、確認済みの個体属性・バリエーション編集を対象とする。編集対象の安全な生成・削除と参照整合性が確認できないものは無効化する。未確認 ID、固有データ、所有権、DLC 権利、プレミアム／オンライン関連の状態を推測・生成しない。通常通貨も別途正確な契約が確認できる場合にのみ対象となり得る。
- インベントリーのカテゴリー内をスクロールしても、検索欄・操作ボタン・カテゴリー切替をヘッダー直下で常時利用できるようにする。
- 所持数量の入力は確定済み数量と区別する。チェック型の確定ボタンは現在の確定数量と異なる入力時のみ表示し、有効な数量だけ確定できる。入力を元に戻した時や当該行の確定・履歴操作後には隠す。他の行の確定で数量・編集条件が変化していない未確定入力を消さない。ロック・履歴操作・新規セーブ読込では該当する未確定入力を破棄する。変更前後の数量差分はカード上に表示しない。未確定状態はチェック型確定ボタンの表示で識別する。Addモードの初期数量1は未実行の追加操作なので確定ボタンを表示する。
- スタックの数量0化（レコードとユニークデータを保持）と、エントリーごとの物理削除（レコード自体を除去）を明確に区別して両方提供する。物理削除は既に数量0のエントリーにも適用可能とする。GetAll等で先行取得した不要なエントリーの除去を用途に含む。コレクション・アチーブメントへの連動は後述の明示的な確認付き操作とし、その他のゲーム進行・報酬・権利情報の自動修復は行わない。個別・一括の両操作を提供し、それぞれ対象と削除方式を明示した確認ポップアップを設ける。一括操作は原子的な履歴1件として Undo/Redo できること。参照整合性を保ち、原本の他のレコードと割当情報を保持する。
- インベントリーへの新規エントリー追加・物理削除（個別・一括・カテゴリー単位）では、原本で確認済みのコレクション登録単位・アチーブメント達成条件に基づき関連状態を連動編集できるようにする。既存エントリーの数量変更・数量0化・補充のみでは連動させない。コレクションは新規追加時の登録、最後の該当エントリーの物理削除時の登録解除を候補とし、他の有効な該当エントリーや確認済みの登録維持条件が残る場合は解除しない。既存の登録日時・達成日時は不要に変更しない。アチーブメントは収集状態から正確に再評価できる条件とその親子関係に限定し、過去の累計行動回数やクエスト、報酬、ゲームカウンター、オンライン実績、権利を推測・変更しない。
- 上記の追加・物理削除でコレクションまたはアチーブメントに実際の連動変更が生じる場合は、実行前に必ず確認ポップアップを表示する。変更対象と登録／解除・達成／未達成・確認済み進捗への影響を簡潔に示し、連動する範囲を選択できるようにする。両機能への変更がない追加に連動確認を出さない。削除・数量0化の既存確認は維持し、削除時の連動確認は同じポップアップにまとめる。キャンセル時は一切変更しない。日時が失われる解除は確認対象とする。連動で新規登録・新規達成し、原本の保存構造に対応する日時フィールドが存在する場合は、ポップアップ表示時点の現在日時を初期値とし、同じポップアップ内で利用者が年月日・時分秒を変更できるようにする。一括操作では新規記録に共通の指定日時を適用する。日時を持たない記録には日時入力を出さず、既存登録・達成日時は保持する。解除で消失する日時は設定対象としない。親子アチーブメントの日時は確認済みの集計規則を優先する。日時の手動指定は実際の過去の取得時刻を証明するものではなく、利用者が明示する編集値として扱う。保存時のタイムゾーン変換・範囲・ネイティブ精度は既存の日時編集と共通化し、Rustで検証する。
- 連動計画、変更前状態とリビジョンの照合、原本由来の対応関係・参照の検証、全対象への適用、復旧、書き出し後の再解析を共通Rust基盤で行う。関連変更を含む1件の原子的履歴とし、Undo/Redoで全変更を一体として戻す／進める。他機能の履歴との依存関係を壊す部分的な履歴操作は許可しない。未確認の対応関係は連動対象外とするが、安全な独立インベントリー編集まで妨げない。
- 既存スタックの数量変更・数量0化・補充・物理削除の可否は、ユニークデータの属性編集・複製・新規生成の可否と独立させる。既存レコードの構造、識別子、必要な数量上限・参照関係を検証し、数量操作では未編集のユニークデータのバイト列を完全に保持する。物理削除は対象レコード全体を除去し、ユニークデータの具体的な値の解釈や生成ルールが未対応であることだけを理由に禁止しない。共通構造ごとに一括対応し、必要な参照や特殊な状態の意味が未確認のものは安全に拒否する。
- ゲーム原本に基づく分類・判定の技術資料は [inventory-native-categories.md](inventory-native-categories.md) を参照する。調査済みと実装済みの範囲は本書の製品目標とは区別する。
- 大規模なカテゴリー一括編集は65,536エントリーを初期性能検証目標とする。固定の8,192件等の制限を設けず、実際の対象件数と履歴・処理容量で制御する。Undo/Redoは最大256操作とし、総履歴容量も事前検証する。原子的な一括処理を分割実行しない。容量不足時は変更前に拒否し、復旧に必要な履歴を黙って失わない。
- 同一Item IDの重複した通常スタックは、Rustが参照安全性を確認できる場合、全正数量エントリーを一括で数量0化できる。他に正数量の重複行がない場合は、個別削除ダイアログから最後の正数量行を0化できる。他の正数量行を残す部分0化やロック済み正数量行を含む一括0化は許可しない。原本の各エントリーは保持する。
- カテゴリー単位で数量0化またはエントリー削除を一括実行できる。検索・表示件数・数量0表示設定に依存せず、選択中のカテゴリー全体を対象にし、ロック済みとRustが当該操作を許可しない行を除外する。確認画面で実行方式、対象件数・除外件数を示し、処理は1件の原子的履歴とする。技術上の上限に達する場合は一部だけを黙って実行しない。
- 個別スタックのロック・解除を提供する。カテゴリー単位の一括ロック・解除も可能とする。ロック済みの行は数量変更・追加補充・属性編集・削除・一括選択から除外し、ロック行を変更するUndo/Redo・履歴移動も拒否する。ロックは現在のセーブセッションに紐付いたブラウザ内の保護設定でありゲームセーブに書き込まない。ローカル復旧で保持し、新しい原本を開く際に初期化する。

- 外観だけでは種類を識別しにくい創作料理・飲み物は、メイン画像上部の既存補助領域に原本由来の材料／フレーバー識別アイコンを横並びで表示する。基本材料は省略し、異なる材料は個別に、順序に意味がない同一材料の重複は1アイコンと右下の数字のみの数量（2以上のみ、×は付けない）で表示する。3色ダンゴ等の外観・個体属性に順序が影響する料理、および順序の意味が未確認の材料配列は、同じ材料でも集約せず原本の枠順で個別表示する。数量と順序付き構成を区別する。材料名はホバー等で確認でき、カード高さ・メイン画像位置を変えない。セーブから実際の使用材料が確定しない場合は味・色に対応する原本候補として扱い、複数候補や未確認の材料を断定しない。使用材料が原本で確認済みの複数候補のいずれかである場合は、候補の原本画像を同じ1枠にまとめ、疑問符等の追加マークを付けない。候補名はホバー等で確認できるようにする。タピオカ等の追加材料・数量は原本の属性対応が確認できたものを表示する。創作料理を先行し、通常料理への拡張は識別上の必要性に応じて行う。追加・編集プレビューにも共通適用する。
- インベントリーの全カードでメイン画像の表示領域・中心位置を統一する。補助マークの有無で画像や名称の位置を変えない。マークは共通の固定領域に重ねて表示し、画像の縮尺や視認性を損なわない。編集・追加プレビューもマークの有無で画像位置を変えない。

## 6. Layouts — レイアウト管理と2D配置編集

- 第4の主要機能の英語名称は Layouts。ゲーム原本の正式名称を全対応言語で優先する。Cabins、Player Home、Character Homes、各 Room、および確認済みの同等空間を対象とし、将来の Player Home Landscape・屋外・追加空間にも共通基盤を拡張する。未確認の保存構造・ゲーム版には書き込まない。ゲーム内のオンライン Layouts、Kits、Floorplans とローカルバックアップを区別する。クラウド・共有・アカウント・コミュニティは対象外。
- 第1段階を最優先とする。空間個別・建物単位・全対象のバックアップと復元、任意名称、同一空間の複数保存、ローカルファイル出力、保存日時・対象・版の保持、保存済みレイアウト切替を提供する。バックアップは読み取りのみ。同一セーブ・同一空間の正確な復元を先行し、異なる空間・セーブへの複製・移行は識別子・間取り・所有・参照整合性の根拠が揃ってから対応する。
- Item ID・個体識別子、XYZ・回転・高低差、積み重ね・親子関係・設置先、色・柄・材質・カスタマイズ・ユニークデータ、壁紙・床材・間取り、および復元に必要な未知のネイティブデータを保持する。実フィールドは原本による。表示できない情報も破棄しない。
- 復元前に互換性、参照、欠落家具、競合、変更内容を Rust で検証し、確認後に原子的に実行する。Inventory との所持・配置・収納・個体属性の連動は原本の仕組みに従い、関連変更を一つの CAS/Undo/Redo とする。確認なしの家具生成・増殖・消失・部分復元を禁止し、原本不変、未知データと精度保持、出力再解析を徹底する。
- 第2段階として同じ基盤による2D配置編集を開発する（従来の保留を解除）。原本アイテム画像を使う2Dグリッド上の表示、選択、移動、回転、追加、撤去、複製、複数選択・一括操作、履歴・Undo/Redo、拡大縮小、パンを提供する。ゲーム内の通常配置を優先し、制限超過は正常ロード・保存・再編集・参照整合性の確認後に検討する。3Dエディター・モデル配信・3Dレンダリング・3Dビューアーは対象外。
- 高さ別レイヤー、重なり選択、積み重ね順序・親子関係、積み重ね一括移動、個別高さ変更、必要に応じ側面・断面表示を検討する。具体的 UI は未確定で、原本の座標・配置仕様に基づき決定する。共通の画像・検索・履歴・操作体系を再利用し、全画面を作業領域とする。未対応操作は無効化する。

## 7. 共通データ・画像

- 現段階の画像開発は、コレクション（カテゴリー・個別アイテム）、アチーブメント（カテゴリー・個別実績）、インベントリー（全アイテム・全個体外観）のメインアイコンの網羅を最優先する。着用状態・ミッション・交換等の追加補助表示の開発は、メイン画像の不足解消より後とする。原本に専用画像が存在しない場合は、原本の代替表示経路を確認し、未確認の画像を捏造しない。既存の製品範囲や原本に基づく個体外観の生成方針は変更しない。

- Item ID、GUID 等の正確な識別子で、原本の版・根拠を保持した共通データベース、ローカライズ、画像資産を全領域で再利用する。ゲーム更新に追随できる構造を採用する。
- ゲーム更新時は同一プラットフォームの原本定義・画像依存資産の版間差分を抽出し、追加・変更・廃止を正確な識別子と原本ハッシュで管理する。変更のない検証済み素材は再利用し、変更された原本・描画設定に基づく画像のみ再抽出・再生成する。新バージョンの画像検証とセーブ編集互換性は独立して確認し、未検証の版を対応済みにしない。更新手順は [icon-source-updates.md](icon-source-updates.md) を参照する。
- アイテム画像はゲーム原本のアイコン、素材、色・柄の定義から作成する。Wiki 画像は禁止。色違い・柄物を含め、表示すべき外観に対応するゲーム原本の完成画像が存在する場合はその画像を使用する。ゲーム内のアイテムアイコンとして実際に動的生成される外観について、対応する完成画像がない場合は、ゲーム原本の素材・定義・実際のアイコン生成処理・描画設定を再現し、ブラウザ内で必要になった時点で動的に生成する。ゲーム内の3D外観そのものをアイテムアイコンの生成対象としない。完成画像が存在しない外観を全パターン事前生成して本番配信する方式は採用しない。原本素材の事前抽出・変換・圧縮と検証用のオフライン生成は許容する。画像比較は結果の検証にのみ使用する。画像比較による色・マスク・カメラ・照明の推定や調整を正確な生成方法としない。近似画像をゲームと完全一致と扱わない。独立した共通画像基盤で扱う。動的生成は表示時・外観属性変更時の遅延生成と上限付きローカルキャッシュを基本とし、Item ID だけで異なる個体外観を混同しない。生成規則が未確認の場合は正確な外観として表示しない。対象は花・カスタマイズ衣装／パレット等を含む、ゲーム内で動的に生成されるアイテムアイコン全般に及ぶ。家具（カスタマイズ家具を含む）はゲーム内の通常 UiIcon を使用し、カスタマイズ状態は原本の補助表示・個体属性で区別する。材質編集には原本の色・柄・材質情報を使用する。家具の3D外観生成、カスタマイザーの3Dプレビュー再現、モデル配信は対象外とする。詳細な根拠・既知の制約は [dye-variant-art.md](dye-variant-art.md) と [native-uiicon-colorways.md](native-uiicon-colorways.md) を参照する。

- ユニークデータ付きアイテムでも、ゲーム内の通常インベントリーが個体の色・柄をメインアイコンへ反映しない場合は、原本の共通 UiIcon とゲーム準拠の補助表示を使用する。花由来のキャンドルはこの方式とし、花の種類に対応する原本画像を保持する。固定色ごとに独立した Item ID がある場合はその原本画像を使用する。Wiki 等に掲載される3Dレンダリング画像をゲーム内のアイコンと同一視せず、ゲーム内の表示処理と実機確認を優先する。詳細は [flower-native-icon-route.md](flower-native-icon-route.md) を参照する。

- 花の Effect／Pattern マークは、カラーマークと同じ外周の縁を保持する。縁の内側を四角い原本画像で余白なく満たし、円形に切り抜く。原本素材の不要な外周余白は除去し、模様内部の透明部分は保持する。インベントリー一覧と編集プレビューで共通とする。
